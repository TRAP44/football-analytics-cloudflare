# MatchRadar — правила для AI-разработчиков

Над этим репозиторием работают **два AI-ассистента** и **один владелец**:

| Кто | Роль | Префикс веток |
|---|---|---|
| **Сергей** (владелец) | ставит задачи, принимает решения, **единственный, кто мержит в `main`** | — |
| **Claude** (Claude Code) | разработчик + ревьюер | `claude/` |
| **Codex** (ChatGPT / OpenAI) | разработчик + ревьюер | `codex/` |

Этот файл — общий источник правил для обоих. Claude читает его через `CLAUDE.md`, Codex — напрямую.

## Перед началом любой задачи

1. Прочитай `docs/ai-team/BOARD.md` — кто что делает сейчас.
2. Прочитай последние записи `docs/ai-team/HANDOFF.md` — что сделано и какие решения приняты.
3. Проверь открытые PR. **Не трогай файлы, которые сейчас меняет другой ассистент** в своём открытом PR. Если без этого никак — напиши об этом Сергею, а не правь молча.
   - **Исключение — координационные файлы** `docs/ai-team/BOARD.md` и `docs/ai-team/HANDOFF.md`. Их меняют все PR, поэтому их можно править, даже если они есть в чужом открытом PR, но только аккуратно:
     - меняй только **строки своей задачи** на доске и добавляй **только свою запись** в журнал; чужие строки и записи не редактируй и не удаляй;
     - при конфликте слияния в этих файлах подтяни свежий `main` и **оставь обе версии** (свои и чужие строки), ничего не выбрасывая.
4. Если задачи нет на доске — добавь её в раздел «В работе» со своим именем в том же PR.

## Как работать

- **Никогда не пушь в `main` напрямую.** Merge в `main` автоматически запускает production-деплой (`Quality` → `Deploy production`). Только через Pull Request, мержит Сергей.
- Одна задача = одна ветка = один PR. Ветка: `claude/<коротко-о-задаче>` или `codex/<коротко-о-задаче>`.
- PR маленький и сфокусированный. Не смешивай рефакторинг, редизайн и новую функцию в одном PR.
- Описание PR — по шаблону `.github/pull_request_template.md`: что сделано, зачем, как проверено, кто автор.
- Не удаляй и не переписывай чужую работу без причины, указанной в PR.

## Проверки перед PR

Node 22. Минимум:

```bash
npm ci
npm run check
npm run lint
npm run test:release
npm test
```

Полный набор того, что гоняет CI, — в `.github/workflows/quality.yml`. Если что-то не удалось запустить локально — честно напиши это в PR.

## Правила проекта (обязательно)

- **Фронтенд-ассеты кешируются навсегда.** Если меняешь что-то в `public/` (JS/CSS/HTML), подними ревизию `FRONTEND_ASSET_REVISION` в `public/modules/app-runtime.js` и все `?v=...` / `frontend-asset-revision` в `public/index.html`, `public/admin.html`, `public/status.html`. Контракт проверяет `test/frontend-asset-revision-contract.test.js`.
- **Не выдумывать вероятности и цифры.** UI и тексты показывают только данные из провалидированного payload (см. README, раздел Match Center).
- **Секреты — только в переменных окружения** Cloudflare/GitHub. Никаких ключей и токенов в коде, тестах и PR. Пример переменных — `.env.example`.
- **Безопасность на сервере.** Скрытие элементов во фронтенде не считается защитой; авторизация админки — только серверная.
- **Миграции Supabase** — только с обновлением контрактов и проверкой `npm run verify:supabase`.
- **Бренд:** основной акцент — **янтарный / жёлтый неон** (как в Telegram-канале), тёмная «стадионная» база, чистый современный AI-стиль. Не менять основной цвет без решения Сергея. `MATCHRADAR_BRAND_SPEC_RU.md` местами описывает старый mint-акцент — при конфликте приоритет у янтарного.
- **Без казино/букмекерской визуальной стилистики** и без ставочных функций, пока Сергей явно не решит иначе.
- Тексты для пользователей — на русском, коротко и по делу.

## После завершения задачи

1. Добавь запись в начало `docs/ai-team/HANDOFF.md` (формат описан в файле).
2. Перенеси задачу в `docs/ai-team/BOARD.md` в раздел «На ревью» со ссылкой на PR.
3. Если что-то осталось недоделанным или нашёл проблему вне своей задачи — запиши в «Идеи / найдено по пути», не чини молча.

## Перекрёстное ревью

Каждый PR одного ассистента проверяет другой:

- PR от Claude → Сергей пишет в PR комментарий `@codex review`.
- PR от Codex → Сергей открывает PR в Claude и просит сделать ревью.

Ревьюер не переписывает PR сам, а оставляет замечания. Исправляет автор.

## Code Review Rules

- Главное: баги, регрессии, безопасность (секреты, авторизация, Telegram initData), дубли уведомлений в Telegram.
- Проверь, что при изменении `public/` поднята ревизия ассетов.
- Проверь, что UI не показывает выдуманные вероятности/цифры.
- Стиль кода и мелочи — только если реально мешают читать.
