# Завершение фоновых задач после потери ответа

После transient timeout `complete_scheduled_job` запрос мог уже изменить строку на `done`. Старый код сразу возвращал неуспех и оставлял состояние неизвестным. Это не доказанная причина всех исторических ошибок, но подтверждённый незащищённый путь.

Теперь читаются только `status,lease_token,group_key,locked_until` одной строки по ключу запуска. Чтение ограничено1800мс. Только тот же owner token/group может подтвердить `done`. Если строка всё ещё `running` и запас lease больше3с, допускается один повтор completion с тем же owner token (RPC1800мс). Потерянный второй ответ проверяется ещё одним чтением, третьего RPC нет. Неизвестное состояние остаётся ошибкой. Claim, release, бизнес-задачи и Telegram send не повторяются; SQL и fencing не меняются. Срок lease не продлевается этим кодом.

В обычном успешном запуске нет дополнительных чтений. В плохом случае максимум2RPC+2bounded reads. Строка другого владельца/группы, failed/expired/missing, ошибка чтения или постоянный HTTP отказ не превращаются в успех. Токен не сохраняется в журнал или отчёт. Существующий heartbeat retry независим.

Read-only Observe Live Usage добавляет только флаг `auto_settlement_recovery_enabled` и безопасные агрегаты состояния watchdog. Не читает ID пользователей, текст ошибок/действий или токены. Максимум28GET по7категориям/7000строк; реальные singleton таблицы фильтруются `id=global`. Не включает автоматическое восстановление и не меняет40pending. Неизвестные/некорректные значения остаются `null`/`unknown`.
