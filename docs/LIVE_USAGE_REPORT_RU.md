# Производственные замеры AI и LIVE

Workflow **Observe Live Usage** читает существующие `ops_events` за последние6часов. Это наблюдение за работой приглашённых пользователей, а не нагрузка и не проверка полной production-вместимости.

После слияния:

```bash
gh workflow run live-usage-report.yml --ref main
```

В GitHub Actions результат появится в Summary и artifact `live-usage-report` (`live-usage.json`, `live-usage.md`, хранение3дня). Запуск ручной, только main и окружение background-jobs. Используются те же SUPABASE_URL/SUPABASE_SECRET_KEY либо SUPABASE_SERVICE_ROLE_KEY, что и у действующего Background Jobs. Новый ключ не требуется. Production-данные до слияния этим PR не читались: политика окружения разрешает только main.

## Что показывает

- `ai`, `match`, `live`, `search`: количество записанных клиентских замеров, p50/p95/max. `live` здесь — обновление матча в Mini App. Меньше20замеров помечаются insufficient_samples; пустой набор даёт null, не0мс. Это описательная статистика, не автоматический вердикт SLO.
- LIVE-табло бота отдельно: события запусков, успешные отправки/правки/итоги, ошибки, неизвестные и ожидающие исходы, отложенные попытки, устаревшие снимки, максимум oldestWaitSec, остановки и исчерпание бюджета.
- Строки warning/error/critical по коду. Старые DAILY_DIGEST_* исключены, поскольку функция удалена.

Клиентская телеметрия может отсутствовать, теряться, включать неуспешные операции и не разделяет готовый кеш/новый AI. Число событий не равно числу людей. Счётчики LIVE суммируются по запускам и могут повторно учитывать отложенную попытку; это не число уникальных доставок или людей в очереди. Успешный Telegram API не доказывает своевременное получение или прочтение. Ops-события могут дедуплицироваться: строка не равна одному возникновению ошибки.

## Ограничения и доступ

Только GET к /rest/v1/ops_events. Узкие SQL/REST projections не выбирают ID людей, сообщения, содержимое статьи, токены или полный metadata. До250строк на страницу,4страницы на каждую из3категорий: максимум12последовательных запросов/3000строк. Общий период фиксируется до начала чтения, сортировка created_at desc; offset-pagination не является транзакционным снимком, поздние записи могут сдвигать страницы.

При полном последнем листе категория conservatively truncated, complete=false. Это не подтверждение, что ошибок мало. Неправильный ответ, отказ доступа и сетевой сбой прерывают сбор; upstream-текст не попадает в stdout/artifact. Нулевая активность не считается здоровой доставкой. Скрипт не пишет в БД, не запускает разбор, не обращается к API-Football/Telegram, не меняет квоты и не деплоит Worker.

Allowlist привилегированного аудита расширен только для3уже используемых Supabase bindings нового workflow; защищённое окружение background-jobs обязательно. Секреты доступны лишь шагу чтения. Все Actions закреплены SHA, persist-credentials=false, permissions contents:read.
