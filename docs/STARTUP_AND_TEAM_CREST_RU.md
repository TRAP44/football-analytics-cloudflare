# Первый вход и отсутствующие гербы

Манифест и bootstrap-профиль стартуют одновременно. Серверная авторизация профиля сохраняется; Избранное и показ ленты ждут compatibility и beta gates. После compatibility запрос ленты может выполняться параллельно профилю; сервер отдельно проверяет Telegram и beta-доступ перед маршрутизацией. Runtime из манифеста переиспользуется. Identity timing теперь перекрывается с manifest timing, складывать эти интервалы нельзя. Искусственная пауза120мс после готовой ленты удалена. Telegram SDK загружается defer перед module entry: браузер может разбирать страницу и загружать ресурсы, сохраняя SDK перед инициализацией приложения.

Изолированный benchmark actualmain/branch startup functions,3пары: fixedmanifest80мс/profile80мс/feed40мс. Main326/323/324мс, branch125/123/121мс. Это воспроизведение удалённого waterfall и паузы, не production latency/телефон пользователя.

В главной карточке пустые/невалидные URLs и сетевые ошибки изображения заменяются нейтральным щитом с инициалами; реальные загруженные эмблемы сохраняются. Имя выводится textContent/escapedHTML. Не применяется эвристика по цвету/размеру или сегменту URL default: так можно скрыть настоящий герб.

Отдельный случай со скриншота: provider может отдать camera/image-not-available PNG с HTTP200. Phase1 не утверждает, что исправила этот файл. Manual/main-only protected ObserveLiveUsage имеет optional inspect_crest=false. При true скрипт читает только2конкретных public provider-fixtures cache keys (UTCtoday/yesterday, max2MB каждый), выбирает только FARDU, скачивает до2canonical publicPNG (128KB/512px), выводит только publicteamID/URL/SHA256 иPNGartifact. Credentials остаются только на Supabase; нет providerAPI, Telegram, SQLwrite или rawpayloadoutput. Полученный реальный файл нужен для точного fingerprint, чтобы не подменять настоящий логотип догадкой.

## Параллельный запрос ленты и профиль (launch131)

После успешной compatibility-проверки запускается один запрос `/api/matches` одновременно с оставшимся bootstrap-профилем/runtime. Ответ и ошибка сохраняются в settled promise; `loadMatches` использует тот же ответ после UI-проверок, без второго HTTP. Если за время ожидания сменилась дата, ответ не применяется — используется обычный запрос нужной даты. Snapshot, sequence guard, серверная авторизация, beta/runtime и API-таймаут 6500мс сохраняются. Данные до UI-проверок не отображаются.

Контрольный замер реальных функций startup при искусственных manifest80/profile160/feed100мс: main261/262/262мс, branch181/182/182мс. Это подтверждает удаление последовательного ожидания, но не измеряет телефон/Telegram/production. Попытка preload26модулей при cold100мс/250KB/s дала практически тот же результат (медианы4538→4521мс); массовый preload исключён. Единственный module-entry перенесён в head после deferred Telegram SDK, исполнение остаётся после разбора DOM.

Чат получает имена `lineups.{home,away}.startXI` из сохранённого разбора. Точный вопрос «Кто в старте?» возвращает эти факты без LLM/квоты; при отсутствии — конкретное сообщение о неопубликованных составах. Запасные не включаются, неполные составы не называются подтверждёнными. Для стартового XI лимит отображения1400символов (обычные ответы300), HTML экранируется. Авторизация/ownership и выключатель AI сохраняются. Новых запросов к источнику нет.
