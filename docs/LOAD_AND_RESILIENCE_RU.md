# Нагрузка и устойчивость

## Запуск

`node scripts/isolated-load-check.js` — 21 сценарий runtime с 10/50/100 одновременными вызовами: shared requests, разные запросы и FREE-бюджет, отказ БД, таймауты, HTTP 429, восстановление после 503, повторы чувствительной операции. Транспорт имитируется с задержкой 10 мс; persistent coordinator также имитируется. Никаких реальных платежей или отправок в Telegram.

`Isolated Load and Resilience` в GitHub Actions запускается автоматически для соответствующих изменений в pull request и main, а также вручную через `workflow_dispatch`. Он выполняет полный набор тестов, сценарии отказов, поднимает одноразовый Supabase, проверяет свежую установку/обновление миграций, SQL-квоты и Telegram dedupe, а затем dump/restore схем приложения public/private в отдельной тестовой БД с security acceptance.

SQL-нагрузка: пакеты 10/50/100 запросов при ограничении 20 одновременных psql-сессий. Это защищает тестовый PostgreSQL от исчерпания соединений; такой результат не доказывает работу 100 одновременных соединений. Время включает запуск psql, поэтому не является production HTTP latency.

Результаты runtime и SQL сохраняются в artifacts. Локальные отчёты — `load-results/`, исключены из Git. Автоматический runtime-check также входит в Quality и обязательные проверки deployment.

## Что считается успешным

- Все совпадающие одновременные запросы разделяют один транспортный вызов; после transient failure повтор ограничен.
- FREE-бюджет допускает только заданное число разных обращений: отказ сверх лимита ожидаем, это не сбой приложения.
- При недоступном persistent guard провайдер не вызывается.
- HTTP 429 сохраняет cooldown и не запускает автоматический retry storm.
- Replay coordinator допускает одно побочное действие; повтор завершённой операции блокируется.
- SQL-квота не превышает лимит, Telegram update имеет одного владельца, telemetry учитывает повторы.
- Восстановленная одноразовая база сохраняет schema contract, пользовательские строки и проходит security acceptance.

## Следующие проверки настоящей инфраструктуры

Staging-проверка требует отдельного Worker/Supabase, тестового бота/канала и лимитов провайдеров. Production не является целью этого workflow. Для HTTP-нагрузки отдельно зафиксируйте допустимые p95, процент ошибок и бюджет вызовов; проверяйте 10/50/100 пользовательских сессий и burst, длительное удержание нагрузки, recovery и multi-isolate contention. Текущие результаты — проверка логики и одноразовой БД, не оценка пропускной способности Cloudflare и не доказательство затрат/латентности реальных AI-провайдеров.

Продакшен-мониторинг, rollback и backup workflow существуют отдельно; запуск нагрузочного workflow не отправляет сообщения пользователям и не меняет production.

## Ограниченный soak и burst

`node --expose-gc scripts/isolated-soak-check.js` — 60-секундный прогон в CI. Локально длительность задаётся `ISOLATED_SOAK_SECONDS` (10–600 секунд); первый расширенный прогон выполнен с 120 секундами. Реальные gateway и singleflight работают в одном процессе; транспорт (5 мс) и persistent guard имитируются. Это closed-loop нагрузка: новая волна начинается после завершения предыдущей, без моделирования внешней очереди или нескольких Worker.

Обычные волны — 50 вызовов на 10 разных запросов, всплески — 1000 вызовов на 20 запросов. В ходе прогона повторяются таймауты, отказ guard и восстановление; отдельно проверяются 429, блокировка во время cooldown и восстановление после его естественного истечения. После каждой волны inflight должен быть пуст, транспорт завершён, число повторов ограничено.

Дополнительно production-pruning проверяется на 60 000 просроченных записях в шести структурах памяти: старые записи очищаются, свежие контрольные записи сохраняются, cache остаётся ограничен.

После прогрева и GC измеряется удержанная память: рост heap не должен превышать 16 MiB, RSS — 96 MiB. Это грубые сигнальные границы тестового Node-процесса, а не доказательство отсутствия всех утечек или лимиты Cloudflare. Event-loop p99 и промежуточные замеры сохраняются в `load-results/isolated-soak.json`; длительный прогон в течение часов и реальная HTTP-нагрузка остаются отдельными проверками.
