Как работать: Сергей говорит Codex «возьми задачу N из `docs/ai-team/TASKS_RU.md`». Codex читает `AGENTS.md`, `BOARD.md`, `HANDOFF.md`, берёт **одну** задачу, делает ветку `codex/<коротко>`, открывает PR и переносит строку на доске в «На ревью». Ревью делает Claude, merge — Сергей.

Общие требования ко **всем** задачам (из `AGENTS.md`, здесь ещё раз коротко):
- Цифры и вероятности только из провалидированных данных сервера. Ничего не выдумывать и не «округлять в красивое».
- Нет новых запросов к API-Football сверх явно описанных в задаче. Тариф Pro (7500/день, 300/мин); запросы идут через ретранслятор Supabase (`API_FOOTBALL_BASE_URL`), `/fixtures`, `/fixtures/lineups`, `/fixtures/events`, `/fixtures/statistics`, `/players` в его белом списке есть.
- Без миграций Supabase, если без них можно обойтись. Схема защищена отпечатком: любая миграция — отдельный PR и отдельное решение Сергея.
- Любое изменение в `public/` — подними `FRONTEND_ASSET_REVISION` (формат `<package.version>-launchN`) во всех местах и тестах (см. `AGENTS.md`).
- Стиль «Стадион»: янтарный неон на тёмной базе, три темы (светлая, тёмная, системная). Без казино и букмекерской стилистики. Тексты — по-русски, коротко.
- Состояния: загрузка, пусто, ошибка, «источник временно ограничен». Не показывать пустую или сломанную карточку.
- Проверки: `npm run check`, `npm run lint`, `npm run test:release`, `npm test`; для UI — браузерный smoke на 320–1280 px. Каждая новая логика — с тестом.
- В PR опиши, что НЕ делал, и риски. Если нужно решение Сергея — напиши вопрос в PR, не угадывай.
- Перед началом задачи перенеси на доске свои уже слитые строки из «На ревью» в «Готово» (только свои).
- Главная (`index.html`, `app.js`, `home-*.js`) — общая зона: если в открытом PR Claude меняется главная, не бери задачу, которая тоже её меняет, — напиши Сергею. Стартовый JS почти упёрся в лимит 515 КБ (`test/public-client-performance.test.js`): новый код для главной выноси в ленивые модули.

## Задача 2 — вероятности на карточках для всех главных матчей дня

Сейчас полоска вероятностей на карточке есть только у матчей, которые кто-то уже разобрал (данные из `model_predictions`, сервер отдаёт `aiProbabilities` в истории; см. `getModelProbabilities` в `src/worker.js` и `src/user-data-api-runtime.js`).
Цель: чтобы у главных матчей дня вероятности были заранее, а не только после чьего-то разбора.
Сделать:
- Фоновое задание в cron (`src/scheduled-jobs.js`, под существующим lease-механизмом): каждые N минут выбирать до K ближайших матчей, **у которых ещё нет строки в `model_predictions`** (приоритет: матчи избранных команд пользователей, затем топ-лиги), и запускать существующий конвейер анализа, который уже пишет в `model_predictions`. Новый расчёт вероятностей не придумывать.
- Важно (по ревью Codex): `model_predictions.fixture_id` — первичный ключ, первая предматчевая запись намеренно неизменяема (`supaInsertIgnore` в `src/settlement-runtime.js`). Поэтому критерий отбора — «строки нет», а **не** «прогноз устарел»: иначе старый матч попадал бы в выборку при каждом запуске cron, тратил бюджет провайдера, а показанная строка всё равно не менялась бы. Если нужен обновляемый прогноз — это отдельное хранилище и отдельное решение Сергея, не в этой задаче.
- **Отдельная системная точка входа** (по ревью Codex): единственный текущий вход в анализ — `apiAnalyze`, он требует пользователя, списывает его квоту, проверяет права, пишет в его историю и события роста. Из cron так нельзя: это либо упадёт на авторизации, либо незаметно спишет квоту с чужого аккаунта. Нужен системный вход, который сохраняет блокировку матча (`distributed-analysis-lock`) и бюджет провайдера, но **не трогает** квоту пользователя, права, историю и события роста. В тестах — проверить, что ничего из этого не вызывается.
- K, N и дневной потолок — конфиг (переменные в `wrangler.jsonc` + `.env.example`), по умолчанию консервативные. Уважать `dailyReserveDecision` и cooldown провайдера: при ограничении источника задание тихо пропускается.
- Телеметрия (`ops_events`): сколько посчитано/пропущено и почему. Без шума: одна агрегированная запись за запуск.
- Сервер отдаёт провалидированные `aiProbabilities` для матчей ленты (`/api/matches`) из `model_predictions`, независимо от истории пользователя; сумма 98–102, иначе поле не отдаётся.
- **Фронтенд обязателен** (по ревью Codex): сейчас `matchCardHtml` рисует полоску только через `aiConfidenceMeterHtml(analysisHistoryForFixture(...))`, а `analysisHistoryForFixture` возвращает лишь запись из истории пользователя с `aiSignalLabel`. Карточка должна брать вероятности из поля матча ленты, если записи в истории нет; подписи и цвета — как у существующей полоски. Подними ревизию ассетов и учитывай лимит стартового JS.
Критерии: тесты на выбор матчей (матч со строкой в `model_predictions` не выбирается повторно), потолки и пропуск при cooldown; тест карточки **неразобранного** матча с вероятностями из ленты; без роста запросов к провайдеру сверх потолка; описание в PR, сколько запросов к API-Football уходит на один матч.
Не делать: LLM, новые таблицы.

## Задача 5 — слой «объяснение на человеческом языке» (Cloudflare Workers AI)

Цель: объяснение матча простыми словами, в котором **невозможно выдумать** ни число, ни вывод. Числа, выводы и сами формулировки фактов — на стороне сервера; LLM только выбирает и упорядочивает.

Архитектура (по ревью Codex: ссылки на факты сами по себе не доказывают, что факт подтверждает фразу):
- Сервер собирает **каталог фактов** матча из провалидированных данных: у каждого факта ID, тип и **каноническая формулировка, сгенерированная сервером по шаблону** (например, `f1` → «Хозяева выиграли 4 из 5 последних матчей», `f2` → «Модель оценивает победу хозяев в 54%»). Тексты фактов пишет только сервер.
- У каждого факта в каталоге сервер сам задаёт **роль** по его типу (`lead` / `support` / `risk` / `caveat`): например, «ключевой игрок хозяев не сыграет» — всегда `risk`, «хозяева выиграли 4 из 5» — `support` для хозяев. Роль задаёт только сервер.
- LLM получает каталог и возвращает **только** упорядоченный список `factIds` (3–5 штук). Ни текста, ни связок, ни ролей LLM не возвращает (по ревью Codex: если бы LLM выбирал связку, он мог бы вывести «Риск:» перед фактом, который риском не является).
- Итоговый текст сервер собирает детерминированно: фраза-связка **по роли факта** из фиксированного набора («Главное:», «Это подкрепляет то, что», «Риск:», «Важно учитывать:») + каноническая формулировка факта. Любой ответ LLM, который не является массивом известных `factIds` без повторов и лишних полей, отбрасывается целиком → показывается порядок фактов по умолчанию (детерминированный, без LLM).
- Так качественное утверждение вроде «хозяева контролируют игру» физически не может появиться: в каталоге его нет, а свой текст LLM вставить не может.
- **Модель — Cloudflare Workers AI** (решение Сергея 10.10.2026: бесплатно в пределах дневной квоты Cloudflare). Подключение — биндинг `"ai": {"binding": "AI"}` в `wrangler.jsonc`, **без API-ключа и секретов**, поэтому задача 0 для неё больше не нужна. Модель — небольшая инструкционная (например, из семейства `@cf/meta/llama-*-instruct`; конкретную выбрать по цене в нейронах и качеству выбора фактов, обосновать в PR). Русский язык модели не важен: текст собирает сервер.
- Бюджет: дневной потолок вызовов в конфиге, учёт в телеметрии; при исчерпании квоты, ошибке или таймауте — молча порядок по умолчанию (без LLM). Переключатель отключения в runtime controls, лимит на пользователя в день.
- **Кеш:** ключ = `fixtureId` + `analysisVersion` + **стабильный хеш каталога фактов** (после нормализации). После обновления составов, событий, счёта или вероятностей текст на старых данных не показывается.
- Нейтральные формулировки уже сделаны отдельно (Claude, `src/signal-wording.js`): используй `NO_CLEAR_SIGNAL_LABEL` и не возвращай ставочную лексику.
Критерии: работает без биндинга и при исчерпанной квоте (порядок по умолчанию); тесты: (1) в итоговом тексте только канонические формулировки фактов и связки, соответствующие роли факта, (2) ответ LLM со свободным текстом / неизвестными ID / повторами / лишними полями (в т.ч. попыткой задать связку или роль) отбрасывается целиком, (3) изменение любого факта → промах кеша; в PR — замер нейронов на одно объяснение и оценка, сколько объяснений в день помещается в бесплатную квоту.
Не делать: свободный текст от LLM в интерфейсе, свободный чат (это задача 6).

## Задача 6 — вопросы по матчу («Спросить про матч»)

После задачи 5. Пользователь задаёт короткий вопрос по конкретному матчу. Ответ — **только** выбор фактов из того же серверного каталога (LLM возвращает лишь `factIds`, роли и текст задаёт сервер), либо готовый ответ «В данных этого матча этого нет». Ключ кеша дополнительно включает нормализованный текст вопроса.
Сделать: поле вопроса + 3–4 готовые подсказки («Почему такой прогноз?», «Что может изменить исход?», «Кто в форме?»), счётчик лимита пользователя, понятные ответы «в данных этого нет», защита от попыток увести разговор в другие темы и от просьб дать ставку. Включается через runtime controls.
Критерии: тесты на отказ вне темы, лимиты, отбрасывание свободного текста от LLM, ответ «в данных этого нет».
