# Очередь задач для Codex (написал Claude, порядок = приоритет)

Как работать: Сергей говорит Codex «возьми задачу N из `docs/ai-team/TASKS_RU.md`». Codex читает `AGENTS.md`, `BOARD.md`, `HANDOFF.md`, берёт **одну** задачу, делает ветку `codex/<коротко>`, открывает PR и переносит строку на доске в «На ревью». Ревью делает Claude, merge — Сергей.

Общие требования ко **всем** задачам (из `AGENTS.md`, здесь ещё раз коротко):
- Цифры и вероятности только из провалидированных данных сервера. Ничего не выдумывать и не «округлять в красивое».
- Нет новых запросов к API-Football сверх явно описанных в задаче. Тариф Pro (7500/день, 300/мин); запросы идут через ретранслятор Supabase (`API_FOOTBALL_BASE_URL`), `/fixtures`, `/fixtures/lineups`, `/fixtures/events`, `/fixtures/statistics`, `/players` в его белом списке есть.
- Без миграций Supabase, если без них можно обойтись. Схема защищена отпечатком: любая миграция — отдельный PR и отдельное решение Сергея.
- Любое изменение в `public/` — подними `FRONTEND_ASSET_REVISION` (формат `<package.version>-launchN`) во всех местах и тестах (см. `AGENTS.md`).
- Стиль «Стадион»: янтарный неон на тёмной базе, три темы (светлая, тёмная, системная). Без казино и букмекерской стилистики. Тексты — по-русски, коротко.
- Состояния: загрузка, пусто, ошибка, «источник временно ограничен». Не показывать пустую или сломанную карточку.
- Проверки: `npm run check`, `npm run lint`, `npm run test:release`, `npm test`; для UI — браузерный smoke на 320–1280 px. Каждая новая логика — с тестом.
- В PR опиши, что НЕ делал, и риски. Если нужно решение Сергея — напиши вопрос в PR, не угадывай.
- Перед началом задачи перенеси на доске свои уже слитые строки из «На ревью» в «Готово» (только свои).
- Главная (`index.html`, `app.js`, `home-*.js`) — общая зона: если в открытом PR Claude меняется главная, не бери задачу, которая тоже её меняет, — напиши Сергею. Стартовый JS почти упёрся в лимит 515 КБ (`test/public-client-performance.test.js`): новый код для главной выноси в ленивые модули.

## Задача 2 — вероятности на карточках для всех главных матчей дня

Сейчас полоска вероятностей на карточке есть только у матчей, которые кто-то уже разобрал (данные из `model_predictions`, сервер отдаёт `aiProbabilities` в истории; см. `getModelProbabilities` в `src/worker.js` и `src/user-data-api-runtime.js`).
Цель: чтобы у главных матчей дня вероятности были заранее, а не только после чьего-то разбора.
Сделать:
- Фоновое задание в cron (`src/scheduled-jobs.js`, под существующим lease-механизмом): каждые N минут выбирать до K ближайших матчей без свежего прогноза (приоритет: матчи избранных команд пользователей, затем топ-лиги) и запускать существующий конвейер анализа, который уже пишет в `model_predictions`. Новый расчёт вероятностей не придумывать.
- K, N и дневной потолок — конфиг (переменные в `wrangler.jsonc` + `.env.example`), по умолчанию консервативные. Уважать `dailyReserveDecision` и cooldown провайдера: при ограничении источника задание тихо пропускается.
- Телеметрия (`ops_events`): сколько посчитано/пропущено и почему. Без шума: одна агрегированная запись за запуск.
- Фронтенд не менять, кроме случая, когда выяснится, что полоска не показывается для матчей не из истории пользователя (тогда: сервер отдаёт `aiProbabilities` для всех матчей ленты, не только из истории; сумма 98–102, иначе скрывать).
Критерии: тесты на выбор матчей, потолки и пропуск при cooldown; без роста запросов к провайдеру сверх потолка; описание в PR, сколько запросов к API-Football уходит на один матч.

## Задача 5 — слой «объяснение на человеческом языке» (LLM) — **после задачи 0**

Цель: LLM только пересказывает уже вычисленные факты простыми словами. Числа и выводы считает движок.
Сделать:
- Серверный модуль (отдельный файл, провайдер-независимый интерфейс), вход — компактный JSON провалидированных фактов матча; выход — короткий текст (3–5 предложений, по-русски, нейтрально).
- **Привязка каждого утверждения к фактам (главная защита):** вход — список фактов с ID (`f1: «хозяева выиграли 4 из 5 последних»`, `f2: «вероятность П1 54%»`…). LLM возвращает **структурированный** ответ: массив предложений, у каждого — непустой список `factIds` из этого входа. Сервер отбрасывает предложения без ссылок или со ссылками на несуществующие ID; если после этого осталось меньше 2 предложений — показывается детерминированный текст из шаблона. Качественные утверждения («хозяева контролируют игру») без подтверждающего факта так не проходят.
- **Дополнительно — числовой валидатор:** любое число/процент/счёт в тексте предложения должно присутствовать в фактах, на которые это предложение ссылается; иначе предложение отбрасывается. Тесты на оба валидатора — главное в задаче.
- Ключ — только переменная окружения Cloudflare (`LLM_API_KEY`, добавить в `.env.example`), **никогда** в коде/чате/PR. Таймаут, лимит на пользователя в день, переключатель отключения в runtime controls.
- **Кеш:** ключ = `fixtureId` + `analysisVersion` + **стабильный хеш входных фактов** (после нормализации). Так после обновления составов, событий, счёта или вероятностей не показывается текст, построенный на старых данных. Тест: изменение любого факта → промах кеша.
- Нейтральные формулировки: убрать ставочные ярлыки (например, «Пропустить ставку» в `src/analysis-runtime.js`, `src/analysis-context-runtime.js`) в рамках этой задачи или отдельным мелким PR. Заменить на «Недостаточно данных для уверенного вывода» и аналогичные.
Критерии: работает без ключа (откат на шаблон); тесты на отбрасывание неподтверждённых утверждений и выдуманных чисел; тест на инвалидацию кеша при изменении фактов; в PR — оценка стоимости одного объяснения.
Не делать: свободный чат (это задача 6).
