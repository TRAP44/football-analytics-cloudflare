# Разовая сверка старых прогнозов

Причина накопления: отчёт39173812212 показал40pending>24ч, auto recovery=false, circuitOpen=false, lastStatus=never. Постоянная настройка остаётся выключенной. Этот режим предназначен для разовой сверки, порученной Сергеем, через существующий settlement runtime; нового публичного HTTP endpoint нет.

В существующем workflow Background Jobs добавлен choice `settlement_recovery`: `off` (default), `preview`, `apply`. Только main и прежнее защищённое окружение background-jobs, прежние секреты и закреплённые actions. Автоматический dispatch без input и schedule сохраняют обычный профиль. Режим передаётся через env, не вставляется в shell-команду.

Preview выбирает только pending и показывает числовые счётчики без provider fixture calls, изменения прогнозов или runtime-настройки. Workflow при этом использует и закрывает обычную глобальную operational lease: это не полностью read-only доступ к БД. Apply использует ту же cron-global lease/heartbeat, runtime controls, схемы, circuit/retry guards, журнал начала/завершения, источник через Supabase relay и прежний settlePredictionsFromFixtures. Другие задачи, Telegram send, AI и постобработка LIVE в этом профиле не выполняются. Параллельная сверка не запускается.

Разовый пакет: максимум40матчей/40дат (обычная автоматика остаётся20/5). Выборка толькоpending не вытесняется историей settled, неполное сканирование останавливает manual apply. Все выбранныеID сохраняются в audit ledger (cap40, раньше20). Квота должна быть подтверждена и больше половины дневного лимита; cooldown и прежний gateway сохраняются. Перед новой датой и перед settlement проверяются ownership, резерв и admission budget120с. Уже выполняющийся запрос не объявляется отменённым; последующие этапы не стартуют при потере права выполнения. Логические запросы по датам могут иметь прежние gateway retries; это не обещание ровно40HTTP.

Официальный источник и существующие правила settlement определяют, можно ли закрыть запись. Переносы, незавершённые матчи, отсутствие результата или несогласованный результат не заменяются выдуманным исходом. Partial — degraded; блокировки — skipped. Счётчики в runner не содержат action IDs, fixture IDs, пользовательских данных или токенов. Сам audit ledger хранит fixture IDs для контроля повторов.

Порядок применения: после CI/review и merge запустить `preview`, проверить counts/guards; затем один `apply`, прочитать итог и повторить Observe Live Usage. Не включать auto recovery и не повторять apply вслепую, если остались записи без подтверждённого результата. Сверка не заменяет подтверждение официальной трансляции/источника и не доказывает доставку уведомлений.
