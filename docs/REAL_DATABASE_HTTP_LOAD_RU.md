# HTTP-нагрузка с настоящим PostgreSQL/PostgREST — 15.10.2026

Тарифы подтверждены владельцем: Cloudflare Workers Free, Supabase Free/Nano, API-Football PRO. Уточнять их заново или переносить токены не требуется.

## Что выполнено

В облачной среде разработки создан отдельный PostgreSQL 16.11 и настоящий PostgREST 16.4. Применены все 39 файлов fresh-install схемы приложения; backend_schema_contract_v2 fingerprint 0169ec29ea39da9d085040ed825057a6 совпал с release-contract.json. PostgreSQL ограничен 512 MiB RAM, 1 CPU и 60 соединениями; PostgREST pool 20. Это заданный профиль стенда, не воспроизведение shared CPU/железа hosted Nano.

HTTP-сервер вызывает настоящую Worker fetch composition в Node 22, авторизация Telegram подписана тестовым токеном. Запросы к БД действительно проходят HTTP → префиксный gateway → PostgREST → PostgreSQL с service_role и production SQL/RPC. Gateway только убирает /rest/v1 и обменивает сгенерированный локальный apikey на соответствующий service JWT; ответы БД не подменяются. База создаётся заново и удаляется после прогона вместе с контейнерами, сетью и временными credentials.

Лента из 120 синтетических матчей и один готовый разбор заранее прогреты в L1. Это не проверка холодного API-Football расчёта или распределённого L2-кеша. База действительно обслуживает users, runtime_controls, model_predictions, квоты/защитные RPC, history, growth/referral operations. Внешний fetch запрещён; провайдер/Telegram/production не вызываются.

В базовой большой ступени: 18 002 настоящих REST-запроса к базе, ответы только 200/201, ошибок нет. SQL после теста подтвердил ровно 10 000 тестовых пользователей и 1000 строк истории. Пик 1000 измеряется барьером одновременного входа HTTP handlers. DB REST concurrency не означает 1000 SQL connections: pool ограничен 20.

## Что означает результат

Функционально нагрузка прошла без ошибок. При отдельной инженерной цели p95 ≤ 2000 мс лента укладывается, готовый разбор на пике 1000 — нет (около 6 секунд). loadPassed проверяет HTTP/DB ошибки; latencyTargetMet показывает цель скорости отдельно. CI не превращает нестабильный межмашинный benchmark в flaky обязательный latency gate. Зелёный job не означает готовность production к массовому запуску.

Следующий измеренный кандидат оптимизации: 8000 REST-операций на 1000 готовых разборов, включая два чтения пользователя. Требуется отдельно проверить возможность объединения в пределах запроса без кеширования/ослабления оплаты, квот и доступа. Теперь getQuota читает текущий plan/expiry и связанную строку usage_daily одним REST-запросом; резервирование и возврат квоты не менялись.

## Границы проверки

- Это настоящая БД в отдельном стенде, но Worker выполняется в Node, не развёрнутом Cloudflare isolate. Free лимит CPU и память isolate не измерены.
- Hosted Supabase Free/Nano, его сетевой RTT, Supavisor, disk/IO и совместное использование CPU не измерены.
- Все клиенты/HTTP handlers находятся в одном процессе; адреса клиентов в локальном gateway синтетические. Cloudflare edge limits и много isolate здесь не тестируются.
- Это короткий burst/ramp с 10 000 открытиями, не 10 000 активных пользователей весь день и не длительный soak с реальной БД.
- Новых/холодных provider analyses, оплат, исходящих сообщений, мобильного интерфейса и AI-пояснений этот прогон не проверяет.
- productionCapacityConfirmed в отчётах всегда false. Боевой Worker и БД не нагружались.

## Воспроизведение

Node 22, Docker, `npm ci`, затем из корня репозитория:

```bash
node scripts/start-real-database-http-load.js
```

Скрипт использует локальный Docker socket с сохранёнными proxy/CA/registry settings; нужны свободные loopback порты 54320/54321. База не публикует порт. PostgREST публикуется только на 127.0.0.1; namespace сети/контейнеров содержит UUID. Все удаления относятся только к ресурсам этого запуска. Образы закреплены SHA256. Полный Supabase CLI image не использован: его PostgreSQL образ не поместился в Docker storage; компактный стек применяет ту же неизменённую схему и проверяет её контракт.

Сценарий требует ACK disposable и принимает только http://127.0.0.1:54321, запрещает production/HTTPS hosts/URL credentials/query/path. Генерируемые ключи существуют только для одноразового стенда и не используют secrets GitHub. При ошибке маленькой ступени повышение нагрузки останавливается; отчёт сохраняется. Старые отчёты перед новым запуском удаляются, чтобы не прочитать результат предыдущего прогона.

Результаты: load-results/real-database-http-{10,50,100,1000}.json и real-database-http-summary.json. В summary записываются SQL evidence, fingerprint и ресурсный профиль. Секреты/сырые error bodies не публикуются. Отдельный job real-database-http в Isolated Load and Resilience воспроизводит весь стенд без ручных действий и без production credentials, artifacts хранятся 7 дней.

## Оптимизация чтения квоты в том же PR

`getQuota` объединяет чтение plan/subscription_until и usage_daily через существующий FK, с фильтром по текущему UTC-дню. Это свежий запрос к БД, не кеш подписки. При ошибке чтения функция по-прежнему отклоняется; просроченный PREMIUM/PRO становится FREE, пустая строка расхода даёт used=0. Записи оплат/резервирование/refund квоты не менялись.

Повтор настоящего ramp: все 10 000 GET + 1000 cached POST HTTP 200, ошибки DB=0, SQL evidence прежний. DB-операции cached POST 8000 → 7000 (12,5% меньше на те же 1000 запросов; аудитория не уменьшается), всего 18 002 → 17 002. p95 этого прогона: лента 2216 мс, готовый разбор 6497 мс. p50 разбора 5263 мс против 5949 мс базового; p95 улучшения не подтвердил. Не выдавать снижение числа запросов за доказанное ускорение: цель p95≤2с по-прежнему не достигнута.

В GitHub предыдущая попытка real-database-http наткнулась на `toomanyrequests: Data limit exceeded` public ECR, до HTTP-нагрузки. Тот же pinned PostgREST SHA256 проверен в официальном ghcr.io/supabase/postgrest, откуда теперь запускается стенд; digest не меняется. Независимый повтор старого job уже прошёл, но новая привязка убирает зависимость от quota ECR.
