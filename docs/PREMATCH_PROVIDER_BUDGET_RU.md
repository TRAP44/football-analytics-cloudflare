# Фоновые прогнозы: замер и резерв API-Football

Первый этап усиления существующей задачи 2 (#831): реальные запросы ограничены отдельно от количества разборов. Вид карточек и скрытые по решению Сергея полоски вероятностей не меняются.

## Воспроизводимый изолированный замер

Node 22: `node scripts/measure-prematch-provider-cost.js`.

Скрипт выполняет настоящий конвейер анализа из композиции Worker. Вместо API-Football и Supabase — локальные подставные ответы; fetch запрещает любые хосты кроме двух тестовых. Ключи из среды не используются. Проверяются полноценный HTTP 200 и повторный ответ из кеша. Данные матчей демонстрационные, не production.

| Сценарий | Запросы API-Football на матч |
| --- | ---: |
| Пустой кеш, за 120 минут до старта | 9 |
| Пустой кеш, за 60 минут до старта | 10 |
| Повторный разбор из кеша | 0 |

Девять запросов: fixture, injuries, predictions, odds, headtohead, форма двух команд, статистика сезона двух команд. В окне составов добавляется lineups. Сценарий использует PRO, обычный взрослый турнир, без судьи и без объявленного состава; расширение данных игроков/судьи и retries могут изменить расход. Это замер конкретных сценариев, **не универсальный максимум**. Все запросы идут через настроенный `API_FOOTBALL_BASE_URL`; тест использует подставной ретранслятор с тем же форматом URL.

Запросы списка матчей при полностью пустом кеше — дополнительно до двух `/fixtures?date`, на запуск, а не на каждый разбор. Они тоже попадают в новый бюджет. `/status` не расходует дневную квоту источника и исключён из него. Supabase-запросы не считаются запросами API-Football.

## Защита живых пользователей

- Потолок сетевых запросов фона — 25% подтверждённого лимита, максимум **1875 из 7500**. Для меньшего тарифа потолок тоже уменьшается. Ограничение числа разборов (сейчас 60/сутки) действует дополнительно.
- Используется атомарный `claim_provider_request` и существующие 24 часовые корзины `prematch-provider-requests:hHH`. Каждый сетевой запрос, включая retry, допускается отдельно. Ошибка чтения/RPC блокирует фон.
- Фон останавливается, если подтверждённый общий расход достиг 50%. Это консервативнее выделения только пользовательского расхода: учитывается и уже потраченный фон.
- Без дневного остатка за текущие сутки или со снимком старше 30 минут фон не начинает расчёт; перед запуском спрашивает бесплатный `/status`, если нужно. Во время расчёта проверка повторяется перед транспортом.
- Функция допуска передаётся только в конфигурацию данного фонового задания. Пользовательская кнопка «Разобрать» не использует фоновый потолок; общие защитные лимиты источника по-прежнему действуют.

Граница: решение принимается по последнему доступному снимку квоты, а не по мгновенной квоте внешнего сервиса. Суточный потолок самого фона атомарен; параллельный внешний расход становится виден при обновлении снимка.

## Выключить без деплоя

GitHub репозитория → Settings → Environments → `background-jobs` → Environment variables → `PREMATCH_PREDICTIONS_ENABLED=false`.

Со следующего запуска GitHub-фона расчёт отключён без изменения Worker. Пустая/отсутствующая переменная оставляет значение wrangler; `true` включает, любое непустое некорректное значение безопасно отключает. Уже выполняющийся запуск не прерывается. Изменение здесь действует на GitHub-фон (текущий `BACKGROUND_JOBS_EXECUTOR=github`), а не на настройки Worker в Cloudflare.

## Журнал и следующие этапы

Одна запись `prematch_predictions_run` в `ops_events` для каждого действительного запуска, включая пропуск из-за бюджета/источника. Поля: посчитано, уже кешировано, пропущено, ошибки, причина остановки, `providerRequestsReserved` и `providerRequestLimit`. Резервирование консервативно: не возвращается при сетевой ошибке. Тики вне интервала/отключённая задача не создают записи.

Далее отдельным PR: единая отметка «рассчитано в ЧЧ:ММ» в штабе и допустимых карточках. Повторный расчёт каждые пять минут не добавляется.

## Этап 2: пересчёт по объявлению составов

Первый расчёт по-прежнему выбирается один раз (при отсутствии `model_predictions`) в прежнем интервале. На пятиминутных тиках фон дополнительно проверяет **событие публикации**, а не повторно считает вероятности по таймеру:

1. Уже рассчитанные главные матчи в окне 20–90 минут до старта: проверить свежий общий кеш `provider-feature:lineups`. Принимаются только API-Football, правильные ID матча/команд, две команды по 11 уникальных игроков без пересечения; возраст источника ≤ 5 минут.
2. Если события нет, после входа в окно ≤ 65 минут допустима одна проверка `/fixtures/lineups` на матч. Попытка заранее сохраняется в общем хранилище; максимум `perRun` попыток за запуск. Пустой ответ не приводит к опросу каждые пять минут. Позже событие всё ещё может прийти из общего кеша, обновлённого открытием штаба/уведомлениями.
3. Только подтверждённое событие допускает дополнительный расчёт. Составы закрепляются за этим расчётом из проверенного снимка, поэтому второй запрос lineups не нужен. После успеха сохраняется признак выполненного этапа; повтор того же или изменённого состава не создаёт третий фоновый расчёт.

Исходные приоритеты избранных/главных матчей и потолки 60 разборов + 1875 API-Football запросов сохранены. Проверки события ограничены первыми 40 подходящими матчами, дополнительные расчёты делят `perRun` с первыми. На тиках вне первоначального интервала список матчей читается только из кеша. При ограничении источника фон останавливается, при ошибке хранения пропускает проверку.

Признак выполнения проверяется также внутри существующей распределённой блокировки матча. Если первый разбор уже включал тот же подтверждённый состав, новый расчёт не нужен. Общий кеш разбора содержит признак этапа и сохраняет его при последующих пользовательских анализах; отдельный признак хранится три дня. Записи `model_predictions` сохраняют прежнюю семантику FIRST/ignore-duplicates: первая предматчевая вероятность не перезаписывается; обновляется рабочий разбор в общем кеше для штаба.

Для критичных записей этого этапа `setCache(...,{requireDurable:true})` подтверждает общее хранилище и не оставляет в памяти ложный успех после ошибки. Обычные вызовы кеша сохранили прежнее поведение. Если обновлённый разбор не удалось сохранить, этап не считается успешным. Неудачная попытка проверки составов не повторяется автоматически; свежий общий снимок всё ещё может активировать событие позже.

Дополнительный изолированный замер: `node scripts/measure-prematch-provider-cost.js --lineup-refresh`. В сценарии с уже прогретым разбором/объявленным составом — 4 запроса (статистика сезона двух команд с предыдущим пустым ответом и игроки двух команд); повтор события — 0. Отдельная первичная проверка составов добавляет до 1 запроса на матч, если её нельзя обслужить из кеша. Истечение остальных кешей и реальные составы/страницы игроков меняют расход; **4 не является универсальным максимумом**, все реальные отправки/retry по-прежнему проходят суточный бюджет.

В журнале добавлены `lineupProbes`, `lineupRefreshed`, `lineupSkipped`. Фактическое время чтения источника используется вместо округлённого cron-слота: задержка запуска GitHub не делает новый снимок квоты/составов «из будущего» (исправление сравнения из #894).

Проверка после production-деплоя: у заранее рассчитанного матча с объявленными составами открыть штаб и проверить стартовые XI и новое `generatedAt`; в ops_events должен быть один `lineupRefreshed`, на последующих запусках — без повторного расчёта. Первая строка `model_predictions` остаётся с прежними captured_at/вероятностями. Старые карточки Telegram автоматически не переписываются.

Границы: нет гарантии обновления каждого матча — действуют малая группа, бюджеты, свежесть и наличие полного состава. Если единственная проверка была раньше публикации/при недоступном источнике и общий кеш позднее не обновлялся, дополнительный расчёт пропускается. UI, скрытые полоски и единая пользовательская подпись времени пока не меняются. Далее остаётся единое время расчёта в штабе/допустимых карточках.

## Этап 3: наблюдаемые матчи в приоритете

«Следить» в Mini App хранится только на устройстве, поэтому серверный признак наблюдения — включённое Telegram-напоминание (`match_reminders.enabled = true`). Порядок очереди: матчи с напоминанием → матчи избранных команд → главные → интерес/время старта. Матч с напоминанием попадает в кандидаты, даже если он не из главных лиг, но окно 20 минут – 36 часов и фильтры молодёжных/товарищеских/низших лиг для него действуют как раньше.

Напоминания читаются одним `select fixture_id` на каждые 200 подходящих матчей (не более 1000 матчей), только из Supabase; API-Football не вызывается. Ошибка чтения не останавливает фон — остаются прежние приоритеты. Бюджеты, `perRun` и потолки не менялись: приоритет меняет только порядок. В журнале добавлено поле `watched` — сколько кандидатов с напоминанием.
