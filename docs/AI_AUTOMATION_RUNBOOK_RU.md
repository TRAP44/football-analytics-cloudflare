# MatchRadar: безопасная автоматизация Claude + Codex

Статус: **подготовка, не готово к автономным merge/релизам**. Основная защита `main` активна, но необходимые обязательные CI checks и проверяемый человеческий merge gate отсутствуют. Пользователь выполнил ручной анализ PR #789 через GitHub в Codex; это **не подтверждает** настройку автоматического GitHub Code Review от Codex.
Целевой репозиторий: `TRAP44/football-analytics-cloudflare`; основная ветка: `main`.

## Цель
Максимально автоматизировать разработку Telegram Mini App **MatchRadar**, сохранив контроль владельца над релизом. Не заменять действующие Cloudflare Workers, Supabase, API-Football, GitHub Actions Quality и Deploy Production.

## Процесс
1. Владелец создаёт или утверждает GitHub Issue с описанием результата и проверяемыми критериями.
2. **После внедрения реального merge gate** оркестратор назначает ограниченную задачу Claude. Claude создаёт ветку `ai/claude/<issue>-<slug>`, проверяет изменение и открывает **Draft PR**. До этого этапа автоматические записи в репозиторий отключены, разрешён ручной или read-only анализ.
3. GitHub выполняет соответствующие Quality, CodeQL и security jobs. Инициатор сверяет их статус с **точным head SHA**; пропущенная из-за `paths-ignore` проверка не считается успешной.
4. После настройки и подтверждения доступности Codex Cloud Code Review (ChatGPT Plus) независимо анализирует фактический diff. Публикация review в GitHub должна быть проверена на практике; текущий ручной анализ через GitHub не является свидетельством работающей автоматической проверки. Ревью ИИ не заменяет тесты, approvals и решение владельца.
5. Claude исправляет обоснованные замечания в своей ветке и снова проходит проверки. Максимум **2 автоматические итерации исправлений на PR**, затем эскалация владельцу. Конкретные лимиты времени и бюджета задаются исполняемым оркестратором до запуска.
6. Владелец изучает diff, замечания и результаты проверок, затем самостоятельно принимает решение о merge. Это пока **организационная мера, не серверная блокировка**; агентам нельзя выдавать merge-capable доступ до реализации и негативного теста merge gate.
7. Только действующий доверенный `Deploy Production` отвечает за production. AI-агенты не вызывают его напрямую.

## Блокирующая предпосылка: защита main
Первоначально 10.10.2026 ветка была без защиты; после ручной настройки владельцем GitHub подтвердил активный `MatchRadar Main Protection` ruleset для `main` с запретом удаления и force-push, требованием PR и без bypass. **Обязательные status checks и человеческое approval пока НЕ установлены** — они остаются отдельными задачами.

Откройте `Settings > Rules > Rulesets > New branch ruleset` для целевой ветки `main`:
- Требовать Pull Request и запретить прямой push / force-push / deletion.
- Запретить bypass, включая администратора, если план GitHub поддерживает этот вариант.
- Зафиксировать обязательные checks **только после исправления их coverage**. У существующего `Quality` есть `paths-ignore` для `docs/**` и `**/*.md`: если сделать текущий Quality обязательным без изменений, Markdown-only PR может зависнуть без check. Разработать отдельный всегда запускающийся PR merge-gate, который подтверждает надлежащие CI outcomes для изменённых файлов; не ослаблять существующий `Deploy Production` и не запускать его ради docs-only PR. Не считать статус `skipped` или отсутствие запуска за успех. Обеспечить защиту самих workflow и ветки от обхода агентом.
- Человеческое утверждение: реализовать проверяемый GitHub-side gate. Предпочтительно **required approving review ≥1** от отдельного человека, который не является автором PR (например, владелец одобряет PR, созданный отдельной учётной записью бота). Если владелец единственный участник и сам автор PR, он не сможет одобрить собственный PR — нужна отдельная, проверенная схема. **Требование PR + устное правило «только владелец нажимает merge» не защищает от merge через API**. После выбора схемы выполнить негативный тест агентскими правами: PR создаётся/обновляется, но merge без независимого одобрения отклоняется.
- Не назначать AI-агентам bypass. Не включать auto-merge.
- Проверить настройки действующего environment `production` отдельно; AI-агенты не должны иметь к нему доступ.

Доступный GitHub connector не имеет полномочий изменять branch protection/rulesets, поэтому правила создаёт владелец в GitHub Settings.

## Подключение провайдеров (следующий этап)
- Claude: установить официальный Claude GitHub App и отдельно настроить минимально разрешённый workflow на `anthropics/claude-code-action`; авторизация через защищённый GitHub Actions secret (например, `ANTHROPIC_API_KEY` или `CLAUDE_CODE_OAUTH_TOKEN` при поддержке).
- Codex: **приоритет — Codex Cloud Code Review через ChatGPT Plus**, без отдельного OpenAI API key. Владелец открывает Codex, подключает GitHub только к `TRAP44/football-analytics-cloudflare`, включает Code review, затем на отдельном PR проверяет `@codex review`; после успешного теста — Automatic reviews. В Plus действуют лимиты Codex, а доступ к Codex Cloud зависит от доступности для аккаунта. 
- Альтернатива `openai/codex-action` с `OPENAI_API_KEY` требует отдельной оплаты API; она не активируется при варианте Plus. Черновик PR #791 — необязательный API-пилот, не предназначенный для объединения в рамках Plus.
- Использовать только проверенные официальные экшены, зафиксированные на commit SHA после аудита, избегать запуска в привилегированном `pull_request_target` на недоверенном коде.
- В целях безопасности держать исходный код PR и любые пользовательские сообщения недоверенными. Не делиться Production-секретами ни с одним AI job.
- Держать выделенные лимиты расходов, защиту от циклических комментариев и разрешённый список запускающих пользователей.

## Порядок внедрения
**Этап 0** — аудит, отдельная ветка и инструкции агентам (этот PR): только документы, никакого включения workflow.
**Этап 1** — базовая защита `main` включена. Не завершён: реализовать human-only gate, обязательные CI-проверки для всех типов PR и проверить permissions/потенциальное право бота выполнить merge.
**Этап 2** — проверить доступность **настоящего GitHub Codex review**, а не только текстового отчёта в Codex с использованием GitHub. Ручной анализ PR #789 уже выполнен, но GitHub-review от Codex не подтверждён. При доступности проверить `@codex review` на тестовом PR и факт появления review в GitHub; лишь затем включить Automatic reviews. Для Codex Cloud по Plus отдельный `OPENAI_API_KEY` не нужен.
**Этап 3** — после настройки Codex Cloud создать отдельный PR для Claude issue-to-draft-PR с минимальными разрешениями и ограничениями расходов, проверить запуск на изолированной задаче.
**Этап 4** — ограниченный оркестратор очереди задач, бюджеты, не более заданного числа циклов, human release gate.

## Красные линии
- Никакого изменения названия, случайной переработки UI и потери русской локализации.
- Никакого изменения существующих PR, в том числе незавершённых исправлений, без отдельного поручения.
- Никакого ручного или AI-triggered production deploy, изменения production SQL, API keys, Telegram bot token или оплат.
- Слияние PR в `main` потенциально запускает production. Его делает только владелец после проверок.

## Критерий готовности автоматизации
Оба AI-провайдера авторизованы с минимальными правами; обязательные проверки проходят или блокируют merge; PR создан ботом как draft; Codex оставляет проверяемый review; Claude исправляет замечания без доступа к Production; владелец один принимает решение о merge; итоговый Production не меняется до этого решения.

## Подписка Plus: сценарий без отдельного OpenAI API
1. Войти в Codex со своим ChatGPT Plus и подключить GitHub-репозиторий MatchRadar (требуется действие владельца при авторизации).
2. В настройках Codex для репозитория включить Code review. Запросить ручную проверку комментарием `@codex review` на безопасном открытом PR.
3. Процесс Draft → Ready: агент создаёт Draft; CI запускается на обновлениях; **владелец** после проверки результатов переводит PR в Ready. Если ручной `@codex review` поддерживается для Draft, им можно воспользоваться до Ready. Автоматическая проверка при Ready допустима лишь после успешного теста реального GitHub-review. При существенном обновлении кода отзыв на прежнем head SHA устаревает: требуется повторное ревью текущего SHA. При отсутствии проверки **не merge**.
4. Кодовые правила находятся в `AGENTS.md` → `## Code Review Rules`. Для их применения во всех PR документ необходимо провести через разрешённый owner-controlled merge после проверки.
5. Codex code review не является обязательной GitHub status check и не заменяет требование approvals; release gate нужно настроить отдельно.
6. Не предоставлять Codex/Claude Cloudflare API token, Supabase service role key, Telegram bot token, API-Football API key, платёжные секреты или прямой доступ к Production.

## Контроль допуска к merge до внедрения автономной разработки
- На 10.10.2026 ruleset `MatchRadar Main Protection` активен, но `required_approving_review_count=0` и обязательных status checks нет. До исправления нельзя считать агенту запрещённым merge технически, даже если он читает `AGENTS.md`.
- Не выдавать ни Claude, ни Codex токены/права, позволяющие merge на `main`, до негативного теста. Конкретные разрешения GitHub App/агентской учётной записи проверить при подключении; они пока не подтверждены.
- Если PR создаёт владелец своим GitHub-аккаунтом, стандартное GitHub approval с требованием одного reviewer нельзя выполнить самостоятельно. Для будущих бот-PR применить раздельные идентичности и review независимого человека либо собственный защищённый owner-only release gate, который нельзя обойти через agent token.
- Кодовые PR требуют реально завершившихся CI-проверок на текущем SHA, а документы `AGENTS.md`/`CLAUDE.md` проходят ручной просмотр владельцем как файлы, влияющие на поведение агентов.
- В GitHub PR или обычном чате отчёт ИИ считается информативным, а не фактом серверного approval. Факт GitHub review и проверок проверяется отдельно.
