# Готовый разбор: очередь БД и пакетная история — 15.10.2026

После #900 готовый разбор на пике 1000 клиентов занимал около 6 секунд. В этой задаче выполнены последовательные сравнения на одном отдельном стенде с настоящими PostgreSQL/PostgREST. Production не нагружался.

## Изменения

1. На существующей cached-ветке запись истории и чтение текущей квоты запускаются параллельно. Ответ по-прежнему ждёт обе операции. Ошибка истории сохраняет старый fail-soft/retry, ошибка quota metadata по-прежнему даёт quota:null для готового разбора. Холодный расчёт и резервирование квоты не менялись.
2. Фоновый full_ai growth event и проверка referral rewards начинаются после завершения этих операций, чтобы не заполнять пул перед чтением, нужным ответу. Вызовы не убраны; waitUntil сохраняется.
3. История в Supabase записывается пакетами до 100 вызовов, с окном накопления 2 мс и ожиданием подтверждения БД каждым caller. Ключ группы — точные supabaseUrl + supabaseKey, конфигурация соединения копируется при постановке в очередь; разные проекты/ключи не смешиваются. При неизвестной identity запись индивидуальная. Дубликаты конфликтного ключа сохраняют самый новый viewed_at, строки сортируются по user/fixture для стабильного порядка блокировок. При отказе batch каждый caller попадает в прежний индивидуальный retry; очереди очищаются перед выполнением записи. getHistory и in-memory storage не менялись.
4. В реальный HTTP harness добавлены p50/p95 REST по операциям и SQL evidence сохранённых full_ai событий. Измерение REST включает очередь/сеть gateway, это не SQL execution time.

## Сравнение

Каждая большая ступень: 10 000 открытий ленты и 1000 запросов одного прогретого разбора, измеренный HTTP peak 1000. Node 22/full Worker composition, PostgreSQL 16.11 512 MiB/1 CPU/max_connections=60, PostgREST 16.4/pool20, одинаковая схема (39 migrations, fingerprint совпадает с release).

| Вариант | p95 ленты | p95 готового разбора | DB REST на 1000 разборов |
| --- | --- | --- | --- |
| До изменений | 1830 мс | 5589 мс | 7000 |
| Только порядок запросов | 1879 мс | 5079 мс | 7000 |
| Пакетная история, прогон 1 | 2162 мс | 4268 мс | 6011 |
| Пакетная история, прогон 2 | 1768 мс | 4461 мс | 6011 |
| Пакетная история + SQL-проверка событий | 1800 мс | 4502 мс | 6011 |
| Пакетная история поверх main с #901 | 1984 мс | 3949 мс | 6012 |

Пакетные прогоны дали p95 3,95–4,50 с против 5,59 с baseline: примерно 19–29% ниже в этом стенде. Число запросов к БД на 1000 разборов снизилось 7000→6011–6012 (примерно 14%). 1000 записей истории в этих прогонах потребовали 11–12 REST upserts вместо 1000; размер пакетов зависит от распределения поступлений, число 11–12 не гарантируется для любого трафика. Каждая строка всё равно записывается в SQL.

Все HTTP ответы 200, REST ответы БД только 200/201, errors=0. SQL evidence: 10 000 тестовых пользователей, 1000 строк истории, 1160 full_ai событий (10+50+100+1000 во всех ступенях). События/referral RPC сохранились; выгода не получена удалением бизнес-функций или фоновых событий. p50/p95 остальных операций доступны в artifacts, без секретов и raw response bodies.

## Проверки и границы

Unit tests: параллельный старт history/quota и отсутствие раннего ответа/аналитики; 1000 ожидающих caller и 10 пакетов по 100; разделение URL/key и неизвестной identity; newest duplicate и стабильная сортировка; ошибка batch и возможность следующей записи; индивидуальные retries двух пользователей после batch failure. Existing cached quota failure, история/retry, квоты, платежи и system analysis regressions сохранены.

Цель p95≤2с пока не достигнута. Эти измерения не подтверждают production capacity: Worker запускается в Node, не Cloudflare isolate; hosted Nano CPU/IO/RTT и много isolate не проверены, данные синтетические, L1 прогрет. Холодные API-Football расчёты/платежи/исходящие Telegram сообщения не нагружались. Никакого кеша оплаты/квот или новых токенов не добавлено; тарифы владельца Workers Free / Supabase Free-Nano / API-Football PRO остаются зафиксированы.

Для повторения: `node scripts/start-real-database-http-load.js`. Результаты и SQL evidence в load-results/real-database-http-*.json; productionCapacityConfirmed=false. Контейнеры/сеть удаляются автоматически. Миграции и public/ не менялись.

После переноса поверх main с #901 финальный повтор дал p95 ленты 1984 мс, готового разбора 3949 мс; все 11 000 HTTP ответов 200, DB REST на 1000 разборов 6012 (12 history batches), SQL evidence прежний: 10 000 users/1000 history/1160 full_ai events. Это ещё один наблюдаемый результат, а не гарантия ускорения в production; цель 2с у разбора не достигнута.
