# Готовый разбор: очередь БД и пакетная история — 15.10.2026

После #900 готовый разбор на пике 1000 клиентов занимал около 6 секунд. В этой задаче выполнены последовательные сравнения на одном отдельном стенде с настоящими PostgreSQL/PostgREST. Production не нагружался.

## Изменения

1. На существующей cached-ветке запись истории и чтение текущей квоты запускаются параллельно. Ответ по-прежнему ждёт обе операции. Ошибка истории сохраняет старый fail-soft/retry, ошибка quota metadata по-прежнему даёт quota:null для готового разбора. Холодный расчёт и резервирование квоты не менялись.
2. Фоновый full_ai growth event и проверка referral rewards начинаются после завершения этих операций, чтобы не заполнять пул перед чтением, нужным ответу. Вызовы не убраны; waitUntil сохраняется.
3. История в Supabase записывается пакетами до 100 вызовов, с окном накопления 2 мс и ожиданием подтверждения БД каждым caller. Ключ группы — точные supabaseUrl + supabaseKey, конфигурация соединения копируется при постановке в очередь; разные проекты/ключи не смешиваются. При неизвестной identity запись индивидуальная. Дубликаты конфликтного ключа сохраняют самый новый viewed_at, строки сортируются по user/fixture для стабильного порядка блокировок. При отказе batch каждый caller попадает в прежний индивидуальный retry; очереди очищаются перед выполнением записи. getHistory и in-memory storage не менялись.
4. В реальный HTTP harness добавлены p50/p95 REST по операциям и SQL evidence сохранённых full_ai событий. Измерение REST включает очередь/сеть gateway, это не SQL execution time.

### Изменение

`recordGrowthEvent` (`src/growth-referral.js`, новый `src/supabase-call-batcher.js`):

- чтение атрибуции — пакетом `GET users?telegram_id=in.(…)&select=telegram_id,acquisition_source,acquisition_campaign,acquisition_content`;
- вставка событий без ключа дедупликации — одним `POST growth_events` массивом, строки в стабильном порядке (telegram_id, created_at);
- окно 2 мс, до 100 вызовов, ключ группы — точные supabaseUrl + supabaseKey, конфигурация копируется при постановке; неизвестная identity — индивидуальный вызов;
- каждый caller ждёт подтверждения базы (waitUntil сохраняется); при ошибке пакета чтения атрибуции — прежнее индивидуальное `getUserRecord`;
- вставка пакетом повторяется по одной (`supaUpsert`) **только** если PostgREST точно отклонил пакет (HTTP 4xx, кроме 408: транзакция откатилась). Таймаут, обрыв соединения, 5xx/шлюз — исход неизвестен: у этих событий нет `event_key`, и повтор задвоил бы уже записанные строки (ревью Codex #928). Тогда событие не подтверждается (`false`), как и прежняя одиночная запись без повтора;
- события с `eventKey` (дедупликация, проверка конфликта) и явной атрибуцией идут прежним путём; при явной атрибуции пользователь больше не читается — результат чтения и раньше не использовался.

Права, подписки, квоты, лимитеры, HMAC/freshness, distributed locks, idempotency, provider reserve, история и награды не менялись; события не удалялись.

#### Красный прогон 9: 65 ответов 503

65 ответов 503 = ровно 65 `record_ops_event_occurrence`, а `claim_provider_request` выполнен 1935 раз (на 65 меньше 2000): эти запросы остановились на **первом** вызове БД — pre-auth лимитере (`security-gate.js`), который при ответе RPC дольше 1,8 с закрывается и отвечает 503 `PREAUTH_RATE_GUARD_UNAVAILABLE` (fail-closed). p95 claim в этом прогоне 1976 мс — выше порога. Код причины в тот момент harness не сохранял — вывод сделан по совпадению счётчиков и коду; теперь отчёт пишет `errorCodes` (`"503 PREAUTH_RATE_GUARD_UNAVAILABLE": N`).

Pre-auth claim — первый запрос каждого из 1000 одновременных разборов, до фоновых событий; пакеты событий меняют только фон. Однако p95 claim на этом стенде во всех прогонах 1,06–1,98 с при пороге 1,8 с (baseline 1,36–1,77 с, с пакетами 1,06–1,98 с) — стенд работает у края fail-closed порога независимо от изменения. После исправления 4 прогона с пакетами (10, 12, 14, 15) — 0 ошибок; 1 отказ на 9 прогонов с пакетами против 0 на 6 baseline. Связь с пакетами не доказана, но и не исключена. Admission, бюджет, лимитеры и порог 1,8 с не менялись, нагрузка не снижалась.

Локальный стенд облачной среды (нативный PostgreSQL 16.15 на 1 CPU + бинарник PostgREST 16.4, `REAL_DB_STAND=native`, всего 2 vCPU на базу, PostgREST и Node) для сравнения непригоден: уже baseline на пике 1000 давал 232–599 ответов 503 — pre-auth limiter закрывается при ответе RPC дольше 1,8 с. С изменением — 684 из 1000 (тот же отказ на первой волне claim RPC, до фоновых событий). Эти прогоны не используются как доказательство ни в одну сторону; режим оставлен для сред без доступа к реестрам контейнеров.

### Цель 2 с не достигнута — следующее измеренное узкое место

p50 разбора ≈2,6–4,9 с почти целиком — три **последовательных** запроса ответа к БД: pre-auth `claim_provider_request` → account `claim_provider_request` → чтение квоты (`GET users` + usage_daily), каждый ≈0,7–1,1 с в очереди пула на пике. Фон их почти не замедлял (p50 claim с пакетами не ниже). Кандидаты, каждый — отдельной задачей с замером:

Тот же pre-auth claim — причина единственного отказа (прогон 9): на этом стенде его p95 близок к fail-closed порогу 1,8 с.

1. Объединить два claim одного запроса в один RPC (`claim_provider_requests(keys[])`) — минус один round-trip ответа; нужна миграция → только после «да» Сергея и `npm run verify:supabase`.
2. Читать квоту параллельно с account claim (чтение без записи; при отказе лимитера результат отбрасывается) — без миграции, но меняет порядок общего конвейера маршрутов; нужно доказать, что отказ лимитера по-прежнему не пишет историю и не тратит квоту.

Pre-auth claim до проверки initData и account claim после неё параллелить нельзя: account bucket нельзя расходовать по непроверенному telegram id.
