# Живое табло любимых команд — правила надёжности

Код: `src/favorite-scoreboard-job.js` (задача `favorite_scoreboard`, cron раз в 5 минут).
Тесты: `test/favorite-scoreboard-job.test.js`. Стенд и замер: `scripts/scoreboard-harness.js`,
`node scripts/scoreboard-capacity-sim.js 1000 10000`. Issue #921.

## Откуда данные и когда снимок считается свежим

- Источник — только кеш `provider-fixtures:<день>:v1` (`fetchedAt`). Новых запросов к
  API-Football и Supabase relay задача не делает.
- Снимок старше **10 минут** (`SNAPSHOT_MAX_AGE_MS`) не создаёт табло и не правит его.
  Возраст считается от фактического времени запуска, а не от слота cron; сдвиг часов
  вперёд до 1 минуты допустим.
  Вчерашний пакет живёт в кеше до 12 часов — именно он раньше давал «LIVE 30′» ночью.
- Снимок, снятый **раньше** уже показанного (`shown.f`), не применяется — счёт и минута
  не откатываются назад.
- Итог матча (FT/AET/PEN) применяется даже из старого снимка; после показанного итога
  табло никогда не возвращается в LIVE.
- Пропуски по устаревшим данным видны в ops-записи (`staleSkipped`, `staleMatches`);
  пользователю технические баннеры не показываются.

## Состояния табло у получателя

Запись `scoreboard:<fixture>:v1` → `users[telegram_id]`, компактно:

| Состояние | Поля | Что значит | Обычные уведомления о голе |
|---|---|---|---|
| active | `m` (message_id), `h` (хеш текста), `a` | Telegram подтвердил отправку | **не** шлём — табло их заменяет |
| pending / unknown | `s:'p'`, `a` | отметка «отправляю» сохранена; ответ Telegram не получен (таймаут, сеть, падение запуска) | шлём (fallback) |
| blocked | `s:'b'` | 403 / бот заблокирован | не шлём табло; уведомления решает их сервис |
| done | `m`, `s:'d'` | итог показан, сообщение удалено или человек отписался | табло больше не трогаем |

`scoreboardRecipientIds` (используется `smart-notification-service` для `match.goal`)
возвращает **только active**. Pending не выдаётся за подтверждённое табло, поэтому
человек с неизвестным исходом отправки не теряет уведомления о голах.

## Политика отправки и восстановления

1. Пачка новых табло одного матча сначала **надёжно** сохраняется как pending
   (`setCache(..., { requireDurable: true })`). Не сохранилось — ничего не отправляем.
2. Отправка. Успех → active. 403 → blocked.
3. **Точный отказ** Telegram (4xx, 429) → отметка снимается, человек вернётся в очередь в
   следующем запуске (курсор откатывается на него).
4. **Неизвестный исход** (таймаут, сеть, 5xx) → остаётся pending. `sendMessage` повторно
   **не** вызывается: возможно, сообщение уже дошло, и повтор дал бы дубль. Человек
   получает обычные уведомления о голах (fallback). Счётчики `unknown` / `unknownPending`.
5. После пачки — одна надёжная запись итогов. Если она не удалась
   (`stopped: 'checkpoint_failed'`), в базе остаются pending-отметки — повторной
   отправки не будет, дубля нет.
6. Правка (`editMessageText`): «not modified» — норма; 403 → blocked; «message not
   found» → done без нового сообщения; прочие ошибки — повтор правки в следующем запуске
   (правка идемпотентна).
7. **Повторная проверка перед правкой.** Получатели уже показанных табло, до которых
   дойдёт запуск, заново проверяются: включены ли уведомления о голах
   (`filterRecipients`) и есть ли команда матча в избранном (`favorites` по их id,
   пачками по 200, не зависит от курсора). Отписался или убрал команду → done, правок и
   итога больше нет (`optedOut`). Проверка не удалась → правки откладываются
   (`recheckFailed`), ничего не отправляется.
8. **Дедлайн 45 с** проверяется перед каждой отправкой, в том числе внутри пачки.
   Неотправленные отметки снимаются, сохраняются и возвращаются в очередь через курсор.
9. **429**: запуск останавливается на первом 429, пауза `scoreboard:pause:v1` до
   `retry_after` (по умолчанию 60 с, максимум час). Следующие запуски до конца паузы
   ничего не шлют (`reason: 'rate_limit_pause'`).

## Очередь, курсор и справедливость

- Болельщики читаются из `favorites` постранично в порядке `(telegram_id, team_id)` с
  составным курсором `scoreboard:discovery:v1` (`after`, `afterTeam`; до 10000 строк за
  запуск). `telegram_id` не уникален, поэтому граница страницы может разрезать команды
  одного человека — следующий запуск продолжает с `(after, afterTeam)`:
  `or=(telegram_id.gt.X,and(telegram_id.eq.X,team_id.gt.T))`. При `truncated` следующий
  запуск продолжает с последней строки; при смене набора идущих
  команд курсор сбрасывается. Поздние пользователи попадают в следующий полный проход.
- Если запуск упёрся в лимит, курсор ставится перед первым необработанным или
  отклонённым новым получателем — никто не выпадает.
- Порядок в запуске: сначала итоги (старые первыми), затем поровну пачки правок
  (самые давние первыми) и пачки новых табло (по матчу и id).
- Ограничения запуска: 600 сообщений (`MAX_MESSAGES_PER_RUN`) и 45 с работы
  (`runTimeBudgetMs`); задача идёт под общей блокировкой cron (lease + heartbeat).
  600 не увеличен: замеры ниже показывают, что упираемся не в него, а в размер состояния.
- Выключатель `FAVORITE_SCOREBOARD_ENABLED=false`: задача ничего не шлёт и не пишет,
  `scoreboardRecipientIds` пуст — все получают обычные уведомления о голах.

## Одна ops-запись за запуск

`FAVORITE_SCOREBOARD_RUN` (или `FAVORITE_SCOREBOARD_PARTIAL` с severity warning, если были
ошибки или неизвестные исходы; без активности запись не пишется),
`meta`: `sent`, `edited`, `closed`, `unchanged`, `blocked`, `failed`, `unknown`,
`unknownPending`, `optedOut`, `recheckFailed`, `deferred` (хвост), `oldestWaitSec` (старейшая ожидающая правка),
`staleSkipped`, `staleMatches`, `capped`, `stopped`, `retryAfterSec`, `telegramCalls`,
`dbWrites`, `discovery {cursor, next, truncated}`, `reason`.

## Замеры (изолированно, `scripts/scoreboard-capacity-sim.js`)

Один матч, cron раз в 5 минут, лимит 600 сообщений за запуск. Telegram и база — в памяти;
реальную пропускную способность Telegram симулятор не доказывает.

| Получателей | Фаза | Запусков | До последнего, мин | Telegram | Записей в БД | Записано, КБ | Страниц favorites | Состояние матча, КБ |
|---|---|---|---|---|---|---|---|---|
| 1000 | первые табло | 2 | 5 | 1000 | 16 | 408 | 2 | 51 |
| 1000 | правка после гола | 2 | 5 | 1000 | 2 | 100 | 7 | 50 |
| 10000 | первые табло | 17 | 80 | 10000 | 151 | 34 572 | 95 | 509 |
| 10000 | правка после гола | 17 | 80 | 10000 | 17 | 8 561 | 220 | 499 |

Страницы favorites в фазе правок включают повторную проверку получателей (до 3 запросов
по 200 id за запуск).

Выводы:

- До ~1000 болельщиков на матч схема укладывается в 1–2 запуска и умеренные записи.
- Массовая доставка 10000 табло этим PR **не решена** — это измеренное ограничение.
- На 10000 табло доходит до последнего за ~80 минут, а каждая запись переписывает
  ~0,5 МБ JSON: ~35 МБ записи за первую раздачу. Для Supabase Free/Nano это дорого.
  Повышать 600 бессмысленно, пока состояние — один JSON на матч.

## Следующая подзадача (нужна миграция — только после «да» Сергея)

Таблица `scoreboard_deliveries` вместо одного JSON на матч:

```sql
create table scoreboard_deliveries (
  fixture_id  bigint  not null,
  telegram_id bigint  not null,
  state       text    not null check (state in ('pending','active','blocked','done')),
  message_id  bigint,
  text_hash   text,
  claimed_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now(),
  primary key (fixture_id, telegram_id)
);
create index scoreboard_deliveries_due on scoreboard_deliveries (fixture_id, state, updated_at);
```

Запись — построчно (`upsert` пачкой только изменённых строк), чтение получателей
`match.goal` — `state = 'active'`. Вместе с миграцией: контракты и `npm run verify:supabase`.
