# Очередь RPC защитного лимитера — 16.10.2026

Исходный runtime: main95e7f0ae после #931. При пике 1000 клиентов 1000 первых claim RPC отправлялись сразу, а затем ещё 1000 account claim. На маленькой БД хвост первой волны иногда превышает 1800 мс: guard отвечает PREAUTH_RATE_GUARD_UNAVAILABLE. Это не HTTP-ошибка PostgREST и не причина увеличивать таймаут или разрешать запрос без подтверждения.

## Изменение

В одном Supabase-клиенте и для одной пары URL/ключ — не больше 128 активных транспортов claim_provider_request с bucket preauth: или route:. До 2048 ожидающих, FIFO; переполнение отклоняется. Остальные RPC/чтения/записи не проходят через эту очередь. Каждый claim остаётся самостоятельным атомарным SQL-вызовом, в том числе при одинаковом bucket. Решения не кешируются и записи не повторяются.

Монотонный дедлайн начинается при постановке в очередь и включает ожидание и транспорт. В fetch передаётся целое оставшееся число миллисекунд. Осталось меньше 500 мс (нижняя граница существующего транспорта) — запрос в БД не отправляется. Истёкший ожидающий запрос удаляется; поздний успешный ответ тоже не разрешает запрос. Активный транспорт удерживает слот до завершения либо до отзыва просроченной аренды (deadline + 250 мс); см. исправления по ревью ниже. Конфигурация соединения, payload и дополнительные заголовки копируются при постановке.

Guard-код, его deadline 1800 мс, проверка Telegram, лимиты, права, квоты, история и схема БД не меняются. При переполнении/истечении действует прежняя обработка ошибки guard. Миграции и production-конфигурация не нужны.

## Границы

Ограничение внутри одного isolate, не глобальная очередь Supabase. На множестве isolate суммарная нагрузка может быть выше. Сетевые задержки выше100мс, длительный hosted traffic, холодные анализы, реальные Telegram-рассылки и платежи здесь не проверялись. API-Football0 на прогретый готовый разбор. Цель стабильного p95≤2с пока не достигнута; productionCapacityConfirmed=false. Нельзя объявлять массовую ёмкость по этим тестам.

При откате Worker возвращается к прежнему транспорту без изменений БД. Дальнейшее сокращение2000claim требует отдельного атомарного SQL-контракта и проверки конкурентных лимитов; объединять решения для одинаковых bucket или повторять неизвестную запись нельзя.


## Контекст запросов Cloudflare

Первый вариант запускал следующий fetch из обработчика завершения другого запроса. Новый тест с AsyncLocalStorage показал потерю контекста; такая передача I/O небезопасна для Workers. Очередь переделана в выдачу разрешений: после await permit каждый caller сам запускает свой transport в исходном контексте. Тест до исправления падал, после исправления проходит. Дополнительно локальный настоящий workerd:40 конкурентных HTTP-запросов через очередь2, у каждого свой исходящий fetch в локальную echo-службу, все40 вернули HTTP200 и собственный ID. Службы после проверки остановлены; это не deployed Cloudflare.


После исправления контекста два полных настоящих DB-ramp прошли: обычный p95 cached2053,02мс и с100мс RTT2482,99мс, оба11000HTTP200, SQL evidence сохранён, externalBlocked0. Сравнение с успешными baseline:2413,90мс без RTT и2655,54мс с100мс RTT. Наблюдаемый выигрыш ~15% и ~6,5% соответственно; не обещание production latency. Pre-auth таймаутов в этих двух прогонах не было, однако это не доказательство отсутствия таймаутов при любом трафике.


## Исправления по ревью Claude — 16.10.2026

Предыдущий head ec667b61 нельзя считать готовым только по зелёному CI: активный слот зависал навсегда, если transport/body или контекст запроса не завершался. Это исправлено в том же PR #933:

- У каждого активного слота аренда до исходного deadline + 250 мс. Любой следующий enqueue/pump освобождает просроченные аренды, посылает abort и увеличивает rateClaimLeaseReaped. Завершение старой операции после освобождения не может уменьшить число чужих слотов (Set токенов, удаление идемпотентно). Живой ожидающий запрос может сам разбудить pump после аренды, даже если больше новых запросов не пришло. Восстановление не зависит от таймера/finally умершего контекста.
- Аборт caller действует и после прихода headers: сигнал очереди передаётся в rawRpc, а fetchWithTimeout объединяет его со своим сигналом. Тело response.json() находится под исходным общим deadline. Старый запрос не повторяется; после abort/просроченной аренды сервер мог уже выполнить SQL, его поздний ответ не разрешает запрос.
- В ожидании одного bucket не больше 16 задач (активные считаются отдельно). Переполнение bucket: RATE_CLAIM_BUCKET_FULL, всей очереди: RATE_CLAIM_ADMISSION_FULL; counters rateClaimBucketFull/rateClaimAdmissionFull. Один bucket не занимает все 2048 ожидающих мест. Решения одинаковых bucket по-прежнему не объединяются.
- Раньше account guard при любой ошибке RPC возвращал fallback (fail-open). Для новых ошибок локального overflow теперь отдельный отказ503 ACCOUNT_RATE_GUARD_BUSY, retry-after1; обходить лимит через переполнение нельзя. Для прочих транспортных сбоев прежний fallback сохранён. Pre-auth по-прежнему обрабатывает отказ своей прежней политикой.
- Чтобы проверка аренды не сканировала все pending на каждом вызове, просроченность проверяется по ближайшему nextExpiry; ожидающие по bucket считаются Map-счётчиком. Активные SQL на сервере могут завершаться после abort: это не глобальный жёсткий лимит на исполняющиеся SQL. Освобождение аренды не означает повтор или принятие прежнего результата.

Регрессии проверяют зависший transport без finally и таймера, пробуждение внутри grace-периода, late-finally без двойного освобождения, горячий bucket, чтение зависшего body после headers через настоящий общий fetch helper и закрытие account guard при overflow. Локальный workerd:40 конкурентных запросов с правильными ID, зависшее тело прерывается по700мс, следующий настоящий RPC проходит. Предупреждений cross-request/different request/hanging promise в логе не было; локальные службы остановлены.

Конфликт с main после #932 разрешён с сохранением обеих записей BOARD/HANDOFF. Миграций нет. Production, Telegram и платежи не затрагиваются. Новые замеры и итоговые проверки — ниже; цифры старого head выше относятся именно к старому head.
